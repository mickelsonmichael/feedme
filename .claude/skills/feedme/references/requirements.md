# FeedMe — Functional Requirements

This file tracks functional requirements for each screen and feature area. Update this file whenever a new feature is added or existing behavior is intentionally changed.

**Format per entry:**

- `REQ-<SCREEN>-<NNN>`: Short description of observable behavior.
- Tag with `[added]`, `[modified]`, or `[removed]` and a brief note when a requirement changes.

> **The web build is deprecated.** Requirements below that describe web-only behaviour ("on web", wide/desktop-web layouts, mobile-web caveats) are kept for history. They are not verified and are not gates for new work — Android is the only supported platform. Do not add new web-specific requirements.

| REQ-FEEDLIST-001 | The feed list shall display items from all subscribed feeds in a single aggregated list. | REQ-FEEDLIST-003 | [updated] The user shall be able to sort items by newest-first or stacked mode. In stacked mode, recent posts — up to 14 days old, or a feed's newest post up to 30 days old — come first, interleaved across feeds so that a feed posting many times a day cannot bury a feed's post from earlier in the week, and otherwise leaning newest-first. Roughly one slot in ten (never immediately back to back) holds an older post as a throwback; throwbacks favour posts a few weeks old, rotate between feeds, include the occasional much older post, and change once per local calendar day. ## Feed Refresh Engine (`feedRefresher`)

These requirements govern the `refreshFeeds()` function and related scheduling logic.

| ID              | Requirement                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-REFRESH-001 | The refresh engine shall fetch feeds with bounded concurrency (default 6) using a worker-pool pattern, so that a user with many subscriptions does not saturate the network radio or the local database.                                                                                                                                                                                                            |
| REQ-REFRESH-002 | Feeds whose `next_fetch_at` timestamp is still in the future shall be skipped (counted as `skipped` in progress) unless the caller passes `force: true`.                                                                                                                                                                                                                                                            |
| REQ-REFRESH-003 | A failure in one feed shall not abort the refresh of other feeds. Each feed's error is stored individually; the total failure count is returned to the caller.                                                                                                                                                                                                                                                      |
| REQ-REFRESH-004 | On a successful refresh (200 or 304), the engine shall reset the feed's `consecutive_failures` counter to 0 and schedule the next fetch based on the feed's learned publication cadence.                                                                                                                                                                                                                            |
| REQ-REFRESH-005 | On a failed refresh, the engine shall apply exponential backoff to `next_fetch_at` using the feed's `consecutive_failures` count.                                                                                                                                                                                                                                                                                   |
| REQ-REFRESH-006 | Each individual feed refresh shall have a 20-second wall-clock timeout. A feed that exceeds this limit is marked failed and progress advances; the in-flight request may continue in the background and will overwrite scheduling if it eventually succeeds.                                                                                                                                                        |
| REQ-REFRESH-007 | [added] When any feed returns an HTTP 429 Too Many Requests response, the engine shall propagate a host-wide rate limit for that feed's hostname for the remainder of the refresh run. Subsequent feeds from the same host shall be skipped rather than contacted.                                                                                                                                                  |
| REQ-REFRESH-008 | [added] The `Retry-After` header from a 429 response shall be parsed as both an integer-seconds value and an RFC1123 HTTP-date. The resulting delay is used to set the host-wide rate limit expiry for the current refresh run.                                                                                                                                                                                     |
| REQ-REFRESH-009 | [added] Feeds skipped due to host-wide rate limiting shall be counted in the `skipped` progress bucket (not `failed`), matching the behaviour of `next_fetch_at`-based skips.                                                                                                                                                                                                                                       |
| REQ-REFRESH-010 | [added] A 429 response shall not be retried. The engine surfaces it on the first occurrence so the host-wide backoff in REQ-REFRESH-007 applies immediately, rather than re-sending requests the server has already refused while holding a concurrency slot.                                                                                                                                                       |
| REQ-REFRESH-011 | [added] The outcome of each feed refresh — error state, cache validators, rate-limit snapshot, learned interval, failure streak, next fetch time and the cumulative success/failure counters — shall be persisted in a single database write. Fields the attempt gave no verdict on are left untouched: a 304 keeps its stored validators, and a wall-clock timeout keeps the existing error message.               |
| REQ-REFRESH-012 | [added] When a feed response declares its own freshness (`Cache-Control: max-age`, or `Expires` measured against the response `Date`), `next_fetch_at` shall be no earlier than the end of that window. `no-cache`/`no-store`/`max-age=0` impose no floor, `s-maxage` is ignored, and the window is capped at 24 hours. The floor applies to 304 responses as well as 200s, and never shortens the learned cadence. |
| REQ-REFRESH-013 | [added] Items shall be written in batched multi-row statements rather than one statement per item, so a feed's write cost scales with the number of batches rather than the number of items.                                                                                                                                                                                                                        |
| REQ-REFRESH-014 | [added] The scheduled background sync task shall be defined while the app's JavaScript loads, not on first registration, so it runs when the operating system wakes the app in the background without showing any screen. A feed fetch that fails without a reason phrase (as HTTP/2 responses have) shall report just the status code, e.g. `Failed to fetch feed: 404`.                                           |
| REQ-REFRESH-015 | [added] Opening the app, or returning to it after a while away, shall not start a refresh when the scheduled background sync finished within the last background-sync interval (the user's background-sync frequency); the posts that sync fetched are shown instead — on return, behind "New posts available" when there are any. A background sync skipped by the Wi-Fi-only setting does not count. With background sync off, or once the interval has passed, the app refreshes as before, and a library with nothing cached always refreshes. |
